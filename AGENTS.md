# AGENTS.md

Guidance for AI agents (and humans) working on **Tatami**, an app that arranges windows on a grid (similar to Divvy). It has two native implementations in one repository:

- **macOS**: menu bar app in Swift, at the repository root (`Package.swift`, `Sources/`, `Tests/`, `Resources/`).
- **Windows**: notification-area app in C# / .NET 10 / WPF, in `Windows/`.

No code is shared between them. They share the translations (`Resources/<lang>.lproj/Localizable.strings`), the settings backup JSON format, the icon design, `README.md`, this file, `THIRD_PARTY_NOTICES.md`, the localization check, and the two GitHub workflows. The design decisions are in `docs/windows-port-plan.md`. A change to a shared behavior should land on both platforms, or say clearly which platform it leaves out.

## macOS

### Build and run

- Toolchain: Swift Package Manager + Command Line Tools. **Xcode is not required** and there is no `.xcodeproj`.
- Build and package: `./scripts/build-app.sh` → produces `build/Tatami.app`.
- Run: `pkill -x Tatami; open build/Tatami.app`
- Always build with the script, not just `swift build`. The script copies `Info.plist`, the `.lproj` folders, the app icon, and `Sparkle.framework` into the bundle, then signs everything from the inside out. A bare executable has no translations, can't load Sparkle, and has no stable permissions.
- Signing: the script uses the keychain certificate named `Tatami Dev` if it exists, otherwise an ad-hoc signature. Override with `SIGN_IDENTITY="..."`. Never commit certificates or private keys (`*.p12`, `*.cer`, Sparkle or NetSparkle key files).
- Version numbers: don't edit `CFBundleShortVersionString` by hand. The build script sets it from `VERSION`, or from `git describe --tags`. Releases are built by `.github/workflows/release.yml` when a GitHub release is published; the tag (for example `v1.2.3`) becomes the version shown in the About panel.
- Releases: the workflow imports the `Tatami Dev` certificate from secrets (`TATAMI_CERT_P12`, `TATAMI_CERT_PASSWORD`) so every release has the same signature, and fails if the app ends up ad-hoc signed. It then builds the DMG (`scripts/make-dmg.sh`), signs it with the Sparkle EdDSA key (`SPARKLE_PRIVATE_KEY`), and uploads `appcast.xml` (`scripts/make-appcast.sh`) to the release.
- The two `ld: warning: search path ... not found` lines come from Command Line Tools and can be ignored. Any other warning should be fixed.
- There is no Mac in some development environments. Swift changes made there can't be compiled locally; the `macos` CI job is the verification. Say so instead of claiming they compile.

### Conventions

- **Swift 6 strict concurrency.** UI and AX code is `@MainActor`. C and AppKit callbacks (Carbon handlers, `NSEvent` monitors) hop back with `MainActor.assumeIsolated`.
- **Don't pass `@MainActor` method references as closures to SwiftUI**, for example `Binding(get: ..., set: settings.setFoo)`. Write `set: { settings.setFoo($0) }`. The method-reference form crashes the Swift 6.3 compiler used on GitHub Actions (signal 6, "SmallVector unable to grow"), even though newer local toolchains compile it.
- **Coordinates.** Code works in Cocoa coordinates: origin at the bottom-left of the primary screen, y pointing up. The AX API uses the top-left origin with y pointing down. Convert only inside `WindowMover` (`flip`). Use `screen.visibleFrame`, which excludes the menu bar and the Dock, as the target area.
- **Grid rows** count from the top: `row 0` is the top row (on both platforms).
- **Opening windows from the menu bar.** Call `NSApp.activate()` and `makeKeyAndOrderFront` inside `DispatchQueue.main.async`, then call `orderFrontRegardless()`. If you activate while the menu is still closing, macOS may ignore it and the window opens behind other apps.
- **Code comments are in Traditional Chinese** (Swift, C#, XAML, scripts, workflows). Match the existing style. Identifiers are in English.
- Keep changes small and match the surrounding code. Don't add dependencies without asking. The only macOS dependency is Sparkle. If you add one, add its license to `THIRD_PARTY_NOTICES.md` and mention it in `about.credits`.
- **Tests.** Unit tests live in `Tests/TatamiTests` and use **Swift Testing** (`import Testing`, `@Test`, `#expect`), which ships with the Command Line Tools. XCTest is not available without Xcode, so don't use it. Run them with `swift test`. Keep logic that can be tested out of AppKit and AX calls. Put it in `nonisolated static` functions, as in `WindowMover.relativeFrame` and `SnapController.zone`, and add tests when you add or change such logic. Things that need real windows, screens, or permissions, such as moving windows, global hotkeys, and Sparkle, are checked by running the app.

## Windows

### Build and run

- Toolchain: .NET 10 SDK and PowerShell 7. Visual Studio is not required.
- Build: `pwsh scripts/build-windows.ps1` → self-contained `win-x64` publish in `build/windows/publish/`, plus `build/windows/Tatami-<version>-Setup.exe` when Inno Setup 6 is installed (`ISCC.exe` from `$env:ISCC`, `PATH`, or `C:\Program Files (x86)\Inno Setup 6`).
- Run: `Stop-Process -Name Tatami -ErrorAction SilentlyContinue; ./build/windows/publish/Tatami.exe`. A second instance exits quietly, so stop the old one first.
- Version numbers come from `VERSION`, or from `git describe --tags`, as on macOS.
- Installer: `Windows/Installer/Tatami.iss`, per-user (`PrivilegesRequired=lowest`, `%LocalAppData%\Programs\Tatami`), so updates never need UAC. `build-windows.ps1` passes `/DAppVersion`, `/DPublishDir`, `/DOutputDir`. Keep the `AppId` GUID unchanged forever; Windows uses it to recognize upgrades. The installer must work with `/SILENT` (NetSparkle runs it that way), so add no interactive `[Code]`. Uninstall removes the `HKCU\...\Run\Tatami` value.
- The app and installer are not code-signed; SmartScreen warns on first run (documented in the README).

### Conventions

- **Layering.** `Core/` has no WPF or Win32 references. Win32 calls live only in `Win32/`, as P/Invoke (`LibraryImport`). Dependencies are `NetSparkleUpdater.SparkleUpdater`, `NetSparkleUpdater.UI.WPF`, and `xunit`; don't add others without asking.
- **Coordinates.** Win32 uses the top-left origin, y down, in **physical pixels**. No flip is needed (`row 0` is the top row). The target area is `MONITORINFO.rcWork`.
- **DPI.** Move other apps' windows and place Tatami's panels with `SetWindowPos` in physical pixels, never through WPF `Left`/`Top`. Scale DIP sizes (panel width 360, snap margin 5) by the target monitor's DPI.
- **Window frames.** Read the visible frame with `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` and compensate for the invisible borders that `GetWindowRect` includes. `ShowWindow(SW_RESTORE)` before moving a maximized window. Windows of elevated apps can't be moved (UIPI): beep, like macOS does when there is no window.
- **Target window.** Capture the foreground window before showing any Tatami window or menu.
- **Settings.** `%AppData%\Tatami\settings.json`, written atomically, same property names as the backup format. Launch at Login is never stored; it is read from `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`.
- **Tests.** xunit in `Windows/Tatami.Tests`; run `dotnet test Windows/Tatami.sln`. Test what's in `Core/`, including `StringsFile` against the real `.lproj` files. Hotkeys, window moving, snap, and NetSparkle are checked by running the app.

## Settings and backups (both platforms)

- **New settings** go in `AppSettings` and `SettingsBackup` on **both** platforms (`Sources/Tatami/AppSettings.swift` + `SettingsBackup.swift`, `Windows/Tatami/AppSettings.cs` + `Core/SettingsBackup.cs`), with `makeBackup()`/`apply` updated, under the same JSON property name. Otherwise export and import silently drop them. New fields must be optional so older files still import. Machine-specific settings, such as Launch at Login, stay out of backups.
- **`platform`.** Each app writes `"platform": "macos"` or `"windows"`. A file without it is a macOS file from before the Windows version. Key combinations are hardware-specific (Carbon key codes vs. virtual-key codes), so importing a file from the other platform keeps everything else, including the shortcuts' names and areas, but drops every key combination (`SettingsBackup.stripForeignKeyCombos` on macOS, its counterpart on Windows) and leaves the current function shortcuts unchanged. Any new platform-specific field needs the same treatment on both sides.
- `KeyCombo` keeps the JSON shape `keyCode`, `modifiers`, `display` on both platforms. A different shape would make the other platform reject the whole file.

## Localization (required for every user-visible change)

The UI language is chosen **inside the app** (Settings → General → Language). It does not follow the system language, and it defaults to English. Supported languages: `en`, `zh-Hant`, `zh-Hans`, `fr`, `de`, `es`, `hi`, `ja`, `ko`, `ar`. Both apps read the same `Resources/<lang>.lproj/Localizable.strings` files.

### Rules

1. **Never hard-code user-visible text.** Use `L("key")`, or `L("key", arg1, arg2)` for `%d`/`%@` formats, in Swift; `Loc.L("key")` in C#; and `{Binding [key], Source={x:Static local:Loc.Instance}}` in XAML. This applies everywhere users can see text:
   - Menu bar menu items (`AppDelegate`) and tray menu items
   - Settings window: tab labels, section headers and footers, toggles, pickers, placeholders, tooltips (`.help`, `ToolTip`)
   - Help window topics (`HelpWindowController`, `HelpWindow.xaml`)
   - About panel credits (`about.credits`, `about.credits.windows`) and any license or copyright text shown in the UI
   - The DMG install guide `Packaging/How to Open Tatami.txt`, which has one section per language
   - Alerts and error messages, such as in `LaunchAtLogin`
   - Default values that users see, such as the default name for a new shortcut
2. **Add every new key to all 10 `Localizable.strings` files** in the same change. English (`en.lproj`) is the reference. A missing translation falls back to English, but don't ship missing keys.
3. **Platform variants.** When the macOS text doesn't fit Windows (System Settings paths, permissions, Sparkle), add `<key>.windows`. The Windows app asks for `<key>.windows` first and falls back to `<key>`; macOS never reads `.windows` keys. Reuse the base key whenever its text is platform-neutral.
4. **Run the localization check** after editing translations or adding keys: `python3 scripts/check_localizations.py` (macOS; `./scripts/check-localizations.sh` does the same) or `python scripts/check_localizations.py` (Windows). It needs only the Python standard library. It parses the `.strings` files itself (reporting file and line on a format error), checks that every language has the same keys as English, and checks that every key used in `Sources/**/*.swift`, `Windows/**/*.cs`, and `Windows/**/*.xaml` exists in English (as `"key"`, or `[key]` in a XAML binding). Unused keys are listed as a reminder; a `.windows` key counts as used when its base key is.
5. Name keys by area, for example `menu.*`, `tab.*`, `general.*`, `grid.*`, `snap.*`, `fixed.*`, `shortcuts.*`, `shortcut.*`, `recorder.*`, `backup.*`, `help.*`, `about.*`.
6. Escape `"` as `\"` and write newlines as `\n` inside `.strings` values.

### Making text update when the language changes

Switching language takes effect immediately. There is no relaunch.

- **SwiftUI views** re-render automatically if they observe `AppSettings`. Wrap new root views with `.localized(settings)`, which sets the locale and switches to right-to-left layout for Arabic.
- **Menu items** get their titles set in `menuNeedsUpdate(_:)`. Add new items there, not only when the item is created. On Windows, tray menu headers are refreshed each time the menu opens.
- **AppKit text outside SwiftUI**, such as window titles and tab labels, must register with `settings.observeLanguage { ... }` and update itself.
- **WPF** bindings to `Loc.Instance` refresh on their own (`PropertyChanged("Item[]")`). Windows set `FlowDirection` from `AppLanguage.IsRightToLeft`.
- The standard About panel reads its content when it opens, so it only updates the next time it is opened. That is acceptable.
- Sparkle's update dialogs use Sparkle's own translations and follow the **macOS system language**, not the in-app language. Don't try to override them.

### Adding a new language

1. Add a case to `AppLanguage` in `Localization.swift` and to its Windows counterpart. The raw value is the `.lproj` name; `nativeName` is written in that language.
2. Create `Resources/<code>.lproj/Localizable.strings` with every key from English.
3. Add the code to `CFBundleLocalizations` in `Resources/Info.plist`.
4. If the language is written right to left, update `isRightToLeft` on both platforms.
5. Add a section in that language to `Packaging/How to Open Tatami.txt`, the install guide shipped inside the DMG.
6. If Inno Setup ships a translation for it, add it to `[Languages]` in `Windows/Installer/Tatami.iss` (guarded with `FileExists` if it is recent).
7. Run the localization check.

Hindi and Arabic translations were machine-written and should be reviewed by native speakers when possible.

## Permissions and system behavior

- **macOS: Accessibility.** Moving other apps' windows requires Accessibility permission. macOS ties it to the code signature: an entry from a differently signed copy stays in the list, looks enabled, and does nothing. When Tatami isn't trusted, it runs `tccutil reset Accessibility <bundle id>` (no admin rights needed) before asking for permission, so users only need to turn the switch on once. The `Tatami Dev` certificate keeps the signature stable across rebuilds and releases, so this is rarely needed.
- **Windows: no permission**, but windows of elevated (administrator) apps can't be moved by a non-elevated Tatami.
- **macOS updates.** `SUFeedURL` in `Info.plist` points to `releases/latest/download/appcast.xml`. `SUPublicEDKey` must match the private key in the `SPARKLE_PRIVATE_KEY` secret; if they don't match, Sparkle rejects every update. Sparkle compares `CFBundleVersion` (the commit count), so releases must be built from a full clone (`fetch-depth: 0`). Tatami's own automatic check runs once at launch; Sparkle's daily schedule is turned off in `Updater`.
- **Windows updates.** NetSparkle reads `releases/latest/download/appcast-windows.xml` and verifies both the appcast (`appcast-windows.xml.signature`) and the installer (`sparkle:edSignature`) with the Ed25519 public key in `Windows/Tatami/Updater.cs`, which must match the `NETSPARKLE_PRIVATE_KEY` secret. It compares `sparkle:version` (the numeric part of the tag, `1.2.3-beta.1` → `1.2.3`). The Windows key pair is separate from Sparkle's, so a mistake on one platform can't break the other's updates.
- **Global hotkeys** use Carbon `RegisterEventHotKey` on macOS and `RegisterHotKey` on Windows; neither needs a permission, and registration fails if the combination is taken. Tools that intercept keys at a lower level, such as BetterTouchTool, PowerToys, or AutoHotkey, can swallow a combination without making registration fail. When that happens, Tatami cannot detect the conflict.
- **System tiling conflicts with Snap.** Users should turn off "drag windows to screen edges to tile" in System Settings → Desktop & Dock (macOS) and "Snap windows" in Settings → System → Multitasking (Windows).

## Releasing

1. Commit and push everything to `main`.
2. On GitHub, create a release with a tag like `v1.2.3` targeting `main`, and publish it. Use semantic versioning: bump the minor version for new features and the patch version for fixes.
3. `release.yml` runs two independent jobs on the same release:
   - `macos` builds, signs, and uploads `Tatami-<version>.dmg`, its `.sha256`, and `appcast.xml`.
   - `windows` builds and uploads `Tatami-<version>-Setup.exe`, its `.sha256`, `appcast-windows.xml`, and `appcast-windows.xml.signature` (`scripts/make-appcast-windows.ps1`).

   One platform failing doesn't stop the other from uploading. If a job failed for a transient reason, re-run that job. If the code needs a fix, fix it, delete the release **and** its tag, and publish again, because the tag must point at the fixed commit.
4. Check the result: both feed URLs should return the new appcasts, the DMG's EdDSA signature should verify against `SUPublicEDKey`, and the installer's signature should verify with `netsparkle-generate-appcast --verify Tatami-<version>-Setup.exe --signature <sig>` (with `SPARKLE_PUBLIC_KEY` set to the Windows public key).

Required repository secrets: `TATAMI_CERT_P12`, `TATAMI_CERT_PASSWORD`, `SPARKLE_PRIVATE_KEY` (macOS), and `NETSPARKLE_PRIVATE_KEY`, `NETSPARKLE_PUBLIC_KEY` (Windows). The Windows job fails early if either NetSparkle secret is missing.

Generating the NetSparkle keys (once):

```powershell
dotnet tool install --global NetSparkleUpdater.Tools.AppCastGenerator --version 2.9.0
netsparkle-generate-appcast --generate-keys   # stored in %LocalAppData%\netsparkle
netsparkle-generate-appcast --export          # prints "Private Key:" and "Public Key:" as base64
```

Put the private key in `NETSPARKLE_PRIVATE_KEY`, the public key in `NETSPARKLE_PUBLIC_KEY` **and** in `Windows/Tatami/Updater.cs`. Keep a secure backup of the key files and never commit them. If either key pair (Sparkle or NetSparkle) is ever replaced, installed copies on that platform stop accepting updates until users install a build with the new public key manually.

## Before finishing a change

1. macOS: `./scripts/build-app.sh` succeeds with no new warnings, and `swift test` passes. Without a Mac, say that the `macos` CI job is the only verification.
2. Windows: `dotnet test Windows/Tatami.sln` passes, and `pwsh scripts/build-windows.ps1` succeeds with no new warnings.
3. The localization check passes (`python3 scripts/check_localizations.py` or `python scripts/check_localizations.py`).
4. Relaunch the app on the platform you changed and check the feature. Also check it in at least one non-English language, and in Arabic if the layout changed.
5. Multi-screen and mixed-DPI behavior can't be tested with one display. Say so explicitly instead of claiming it works.
6. Update the Help window topics if the change affects how users operate the app (add a `.windows` variant if the text differs), and update the README for new features or platform differences.
